:::tip[What You'll Learn]
Filecoin Onchain Cloud's *Keysmith* package provides all the encryption and key management features you need for simple, recoverable encryption of data stored on Filecoin.

Key things to know:
- Data is encrypted in your app before upload. Storage providers only ever see ciphertext.
- Every key comes from the owner's wallet, so there are no keys to store or lose: the wallet can always derive them again.
- Keys are organised in a tree, so you can give access to part of your data without exposing the rest.
- This document is a high-level overview of the main principles of encryption. For more details and power-users, refer to the [Keysmith README](https://github.com/FilOzone/synapse-sdk/tree/master/packages/keysmith).
:::

Data stored on Filecoin Onchain Cloud is public: any provider holding a piece serves it, and anyone with its CID can fetch it. To keep data private, encrypt it before upload. Providers then store and prove ciphertext like any other bytes, and only holders of the key can read it.

Three packages share the work:

| Package | Role |
| --- | --- |
| [`@filoz/keysmith`](https://github.com/FilOzone/synapse-sdk/tree/master/packages/keysmith) | The keys: derives every encryption key from one wallet signature, and shares them |
| [`filecoin-encryption-envelope`](https://github.com/FilOzone/synapse-sdk/tree/master/packages/filecoin-encryption-envelope) (FEE) | The encrypted format: a small plaintext header (the *envelope*), then the ciphertext |
| [`@filoz/synapse-sdk`](/developer-guides/synapse/) | Storage: uploads the encrypted bytes like any others |

```text
your app ──▶ Keysmith ──key──▶ FEE ──encrypted bytes──▶ Synapse SDK ──▶ storage providers
```

## How it works

The owner's wallet signs a fixed message once. Keysmith turns that signature into a **keyspace key**, the root of a tree of keys:

- **Keyspace:** the whole tree, usually one per data set. Whoever holds the keyspace key can read everything in it.
- **Scopes:** named branches, such as `documents` or `agent-memory/notes`. A scope key opens everything below it, and nothing above or beside it.
- **Pieces:** every upload gets its own key, derived from its keyspace or scope. That's what lets you share a single piece safely.

Because every key is derived rather than random, nothing has to be stored. Each encrypted piece carries a small envelope naming its owner, keyspace and scope, so whoever reads it later knows exactly which key to derive, whichever data set or provider the copy came from.

For the full picture, see [Core concepts](https://github.com/FilOzone/synapse-sdk/tree/master/packages/keysmith#core-concepts) and [The key derivation tree](https://github.com/FilOzone/synapse-sdk/tree/master/packages/keysmith#the-key-derivation-tree) in the Keysmith README.

## Scenarios

### Encrypting your first upload

The owner wallet creates a keyspace by signing twice: the second signature checks that the wallet signs deterministically, which the whole scheme depends on. From the keyspace key, Keysmith gives you a key for the new piece and the metadata its envelope records. FEE encrypts with them, and the Synapse SDK uploads the result.

See [Initializing a keyspace](https://github.com/FilOzone/synapse-sdk/tree/master/packages/keysmith#initializing-a-keyspace) in the Keysmith README.

:::caution[Record the keyspace]
The SDK does not record the keyspace for you. Pass the keyspace id and its commitment as data set metadata when you upload, so you can always find it again from the chain. See [Metadata handling](https://github.com/FilOzone/synapse-sdk/tree/master/packages/keysmith#metadata-handling).
:::

### Reading your data back

Download the piece as usual and hand it to FEE with a Keysmith *key resolver*. FEE reads the envelope, and Keysmith derives the right key from what the envelope says. In a later session, the wallet signs once to get the keyspace key back, and the recorded commitment confirms it's the right one.

FEE can also decrypt just a byte range of a large piece, without decrypting the rest.

See [Reading a piece](https://github.com/FilOzone/synapse-sdk/tree/master/packages/keysmith#reading-a-piece) in the Keysmith README.

### Organising data with scopes

Scopes are labels you choose, and they nest with `/`: `finance` contains `finance/invoices`. Use them for data you may want to share separately, such as one scope per app, per agent or per project. Giving someone a scope key lets them read and write that branch and nothing else.

Settle the shape of your tree before you write data: moving or renaming a scope changes every key below it. Scope names are stored in the clear in each envelope, so use opaque ids if the names themselves are sensitive.

See [The key derivation tree](https://github.com/FilOzone/synapse-sdk/tree/master/packages/keysmith#the-key-derivation-tree) in the Keysmith README.

### Encrypting from a session key or agent

A [session key](/developer-guides/session-keys/) can't sign as the wallet, so it can't derive keys itself. Instead, the owner gives it a **Grant**: a keyspace or scope key, wrapped so only that session key can open it. With the Grant, the session key encrypts and decrypts without ever touching the wallet. It still needs the `CreateDataSet` and `AddPieces` permissions to store what it encrypts.

See [Sharing](/developer-guides/private-data/sharing/) for how Grants work.

### Recovering everything from the wallet

If an app loses its cached keys or Grants, the wallet and the stored pieces are all you need. List the wallet's data sets, sign once per keyspace, and derive each piece's key from its own envelope.

See [Recovery](https://github.com/FilOzone/synapse-sdk/tree/master/packages/keysmith#recovery) in the Keysmith README.

### Encrypted uploads from the command line

[Filecoin Pin](/core-concepts/filecoin-pin/) does all of this for you:

```bash
filecoin-pin add ./report.pdf --encrypt
filecoin-pin get <encrypted-root-cid> ./out
```

To encrypt from a session key, log in with `filecoin-pin login --scopes createDataSet,addPieces,encrypt`, and the Filecoin Cloud console sends the session key its Grant. See [Encrypted Uploads](https://github.com/filecoin-project/filecoin-pin#encrypted-uploads) in the Filecoin Pin README.

## Things to know

- **The ciphertext is public.** Anyone can fetch it; only key holders can read it. Its size is visible, and so is any piece or data set metadata you set, such as a file name.
- **Keys don't expire and can't be revoked.** To stop sharing new data, write it under a new keyspace.
- **The wallet is the recovery path.** Lose the wallet and you lose the data.
- **The wallet must sign deterministically** (RFC 6979). Keysmith checks this for you.

See [Be aware](https://github.com/FilOzone/synapse-sdk/tree/master/packages/keysmith#be-aware) in the Keysmith README for the full list.
